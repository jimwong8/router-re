# 强模型指挥 + 免费弱模型执行：成本账与生产模式

> 结论先行：**方向完全正确，但"省在哪"和直觉相反。**
> 主模型用强模型几乎不花钱（占 0.3%）；真正的钱花在两处——**没人看的预热流量（51%）**和**工人读文件产生的输入 token（25%）**。
> 而且这个架构**本机已经跑通并在省钱**：12 个任务里 11 个由免费模型完成，全部通过验收。

---

## 一、本机真实账单（30 天，网关 usage_events）

| model | 请求数 | 输入 tok | 输出 tok | 估算成本 | 占比 | 实际性质 |
|---|---|---|---|---|---|---|
| sensenova-6.8-flash-lite | 104,045 | 38.6M | 41.9M | **$80.53** | **51%** | ⚠ 预热/健康检查，**不是业务** |
| deepseek-v4-flash | 10,164 | 37.2M | 2.49M | **$39.66** | 25% | 工人（OpenCode pM） |
| deepseek-v4.1-flash | 12,777 | 16.6M | 0.40M | **$17.09** | 11% | 主 agent |
| longcat-2.5-preview | 3,272 | 4.50M | 0.03M | $4.52 | 3% | — |
| glm-5.3 | 705 | 3.23M | 0.28M | $3.51 | 2% | — |
| glm-5.2 | 10,390 | 0.12M | 0.39M | **$0.51** | **0.3%** | 主 agent（强模型） |

**三个反直觉的发现：**

1. **主模型用强模型根本不是成本问题**。glm-5.2 三十天只花了 $0.51，占 0.3%。因为它只做"读结论 + 写决策"，token 量极小。
2. **工人比主 agent 贵 2.3 倍**（$39.66 vs $17.09）。原因看 token 结构：
   - 工人：输入 37.2M / 输出 2.49M（**15:1，钱花在"读"**）
   - 主 agent：输入 117K / 输出 392K（**1:3.3，钱花在"写"**）
   - 工人要读大量源码、工具输出；主 agent 只读摘要、写判断。
3. **最大单项开销是预热，占 51%**。`auto-warmup-loop.sh` 每 90 秒轮询全部 159 个 active channel，每次仅 ~121 token（avg_in=59 / avg_out=62），租户字段为空——纯运维流量，比所有工人加起来还贵。

**所以"强模型指挥 + 弱模型执行"省的是真钱，但它省的是 25% 那一块，不是 0.3% 那一块。真正该先动手的是 51% 那一块。**

## 二、研究支持：这条路有硬证据

| 方法 | 效果 | 来源 |
|---|---|---|
| FrugalGPT cascade | **成本降 98%**，质量接近前沿 | TMLR 2024 |
| RouteLLM | **降 85%**，保持 95% GPT-4 性能 | arXiv:2406.18665 |
| Plan-and-Execute | 强模型只做规划，子任务交小模型 | LangChain |
| thrifty（Claude Code 分层委派） | **省约 64%**，gate 质量不变 | 2389-research |
| 前沿 vs 小模型价差 | **25×** | arXiv:2609.32917 |
| per-subagent 分模型 | 混合方案比全 Opus **便宜 3.75×（省 73%）** | 实测博客 |

关键洞见来自 **Plan-and-Execute**：强模型只在"（重）规划"和"生成最终答案"时被调用，执行步骤交给小模型。这正好对上我们的 token 结构——**执行侧吃输入、规划侧吃输出**。

而 FrugalGPT 的核心不只是"先问便宜的"，是**配一个 checker**：便宜模型的答案要过验证，不够格才升级。没有 checker 的 cascade 是省了钱但质量裸奔。

## 三、本机实证：这个模式真的在跑，而且成功

router-re 项目 12 个任务，**11 个由免费模型（beam-free / opencode-zen 免费层）完成**，全部通过四层验收：

| 判据 | 作用 |
|---|---|
| `expect` | 文件真的存在 |
| `min_lines` | 不是空壳 |
| `must_contain` | 关键函数/错误码在里面 |
| `must_build` | `go build ./...` 通过 |

产出不是"看起来像"：我人工核过 `p20-schedule-wire`——`p15.go` 有 `handleGetTimeSchedule`/`handleSetTimeSchedule`、10403/10404 错误码、`dry_run` 分支、路由已在 319/320 行注册、`go build` rc=0。`p20-api-doc` 是 314 行 / 276 端点 / 278 条表格行。

**成本事实**：`beam-free` 和所有 `:free` 模型走本地 opencode-zen 免费层（`10.100.1.18:6446` / `:8097`），**真实支出 $0**。网关 `estimated_cost` 对它们也计了钱（$2.31 / $3.32），所以那个字段是"按参考价估算"，**不等于账单**——拿它当 ROI 证据会高估成本。

## 四、但有硬前提：不满足就会变成"3/3 全编造"

**反面证据（本机真实发生过）**：09-29 用 `dots-3-note-preview:free` 做子代理，3/3 全部编造——报告了不存在的 `/opt/quant-panel/scripts/` 路径，把 1,886 行 / 173,937 字节的 SKILL.md 说成 120 行 / 6,807 字节。此后切回 `deepseek-v4-flash`。

弱模型三种失败模式（来自 `weak-model-worker-training` 的实测）：

1. **说但不做**——写一个计划就停，把摘要当答案
2. **编造**——假路径、假行数、假数字，语气还很自信
3. **跑偏**——同一个查询换五种写法反复试，不给结论

四个可量化的前提条件：

| 条件 | 实测数据 |
|---|---|
| **上下文瘦身** | 363 个工具 schema + 67 个技能 → 弱模型溺死。瘦身后 **64,395 → 10,183 tok/call（−84%）**，三步任务从"做一步就停"变成"一轮做完" |
| **单步可验证** | 一次给一个子目标。给"跑这三条命令并报告"会编出假调用和"E) F) G)"步骤 |
| **每步新上下文** | 同一会话：**8,474 tok/turn @4 条消息 → 50,931 tok/turn @78 条**，尾部开始输出假 tool-call 文本 |
| **机械验收** | 判定标准是"必须执行命令才能答对"，不是看语气。自报"已完成"永远不算 |

还有一条血的教训：**判定子代理可信度，用"必须执行命令才能答对"的探针**。问它"这个文件多少行"——真跑的会调 `wc -l`，编造的会直接给数字。

## 五、生产模式：三层模型分工 + 成本护栏

### 5.1 按 token 形态分配，不按"重要性"分配

| 层 | 模型档 | 干什么 | token 形态 | 成本特征 |
|---|---|---|---|---|
| 规划层 | **强模型** | 拆任务、定验收、做决策、最后审查 | 输出主导，量小 | 占 0.3%，随便用 |
| 执行层 | **免费/最便宜** | 改文件、写文档、跑命令、跑测试 | 输入主导，量大 | 这里是账单主体 |
| 验证层 | **中档，且 ≠ 实现者** | 独立审 diff、跑行为探针 | 中等 | 防 FM-3.2/3.3 |

**判定规则**：一个任务该给哪一层，看它"是否需要判断"。改一个已知文件、按明确 spec 写文档 → 执行层。决定改哪个文件、改完对不对 → 规划层。

### 5.2 三个成本护栏（比换模型更有效）

**护栏 1：砍掉无人监控的自动化流量。**
本机最贵的一项不是模型选择，是预热。原则：任何定时轮询都要回答"它发现问题的频率是多少"。如果 159 个 channel 里一周才坏 1 个，每 90 秒全查一遍就是 100 万倍的过度采样。

**护栏 2：压输入，不压输出。**
工人的钱 96% 花在输入（37.2M vs 2.49M）。所以：
- 瘦身 profile（工具 schema 从 363 降到 ~15）
- 任务说明里给**确切路径**，不要让工人自己 `grep -r` 找
- 禁止 `grep -r $HOME`（会扫 20G 技能目录）

**护栏 3：缓存与复用。**
同一份文件被 4 个工人各读一遍是最蠢的浪费。任务粒度小 + 路径明确，天然减少重复读。

### 5.3 成本记账的正确姿势

- **不要用 `estimated_cost` 做决策**：免费层也被计费，会高估。
- 用 **token 量 × 该 channel 的真实单价**，并标注哪些是免费层。
- 定期核对 provider 真实账单，修正估算模型。

## 六、落地清单（P0 已实施并验证）

| 优先级 | 动作 | 状态 | 实测效果 |
|---|---|---|---|

| **P0** | 日志轮转（8.2M → 88K） | ✅ 已做 | — |
| P1 | 把 12 个任务的验收判据固化成回归测试 | 待做 | 免费模型换人后能立刻发现退化 |

| P2 | 成本看板：按 channel 标真实单价，区分免费层 | 待做 | 让决策基于账单不是估算 |

### 6.1 预热优化的前后对比（真实数据）

改动前：
- 159 个 active channel **全部**预热，每个 `sleep 8`，单轮 20+ 分钟
- 90 秒定时器 + `flock` 防重叠 → 实际是**不停歇地连轴跑**
- 2 小时内打了 **16,231 次**（占该时段全部请求的 97.8%），真实业务只有 ~365 次
- 30 天成本 **$80.53，占总额 51%**

改动后：
- 每个模型只预热**第一个**匹配到的 active channel（`SEEN_MODELS` 去重）
- `max_tokens` 32 → 1（预热只需知道 key 活着，不需要生成内容）
- 间隔 90s → 600s
- 单轮 **17 秒**，日志显示 6 次请求全部 OK
- 实测请求量降到 **1–2 次/分**

**代价（必须说明）**：备用 channel 不再被逐个体检，坏 key 要等到真实流量命中才发现。网关有熔断兜底，但这个延迟是真实存在的。
**推荐的折中**：10 分钟做每模型快检，另加**每天一次凌晨全量抽查**覆盖所有 channel——成本仍比原来低两个数量级。

## 七、边界（诚实说明）

1. **省钱的天花板在"任务能否机械验收"**。能验收的，免费模型能做到 90%+；不能验收的（"这个设计好不好"），弱模型给你的是自信的废话。
2. **弱模型不是"更便宜的同款"，是"需要工程护栏的另一类工具"**。不配护栏直接上，就是 09-29 的 3/3 编造。
3. **省的是 token 单价，不省时间和 review**。并发上限由 review 决定（实测并发 4→83%、8→17%），加更多免费工人不会更快。
4. **免费层的稳定性是外部变量**。opencode-zen 免费层今天能用，不代表下月能用；调度器必须有"免费层不可用时降级到付费便宜模型"的路径，否则整个流水线停摆。
5. **真正的成本结构问题不是模型，是无人监控的自动化**。先砍预热，再谈模型分级。
